# Fix CR-080 of the code review of 2026-11-13

## Context

CR-080 was entered on 2026-11-20 by the task that fixed CR-016 to CR-020: the second review of
its fixes ran two ways in which the files of `--out` could still be written among the frames,
neither a regression (`main` had both). The owner asked for it to be fixed in the same session,
after the merge of that task ("fa merge si apoi rezolva CR-080 tot aici"). The entry is
`confirmed` and says what should hold, no text changes and no figure moves, so the work went
straight from the entry, without plan mode; this file records what was done.

Worktree `DarksCheck/.claude/worktrees/Fix-DarksCheck-CR-080`, branch
`claude/Fix-DarksCheck-CR-080`, from `main` at 5680fdfb.

## The two cases

1. **The links were followed on the output's side only.** A session `S` whose `darks\` is a
   junction to `Lib\idx67\darks`: `darkscheck S --out Lib\idx67\darks` was not refused, and the
   report, the CSV and the maps landed beside the frames.
2. **A link past the 260th character of the output path was not followed** where Windows' long
   paths are off (as on the owner's machine): the folder was opened by its path as typed, the
   open failed, and the link passed for a folder that does not exist yet. A protected folder
   that deep had no identity either.

## What was done

- Requirement: R-026 says both.
- Tests first, each seen failing on `main`'s code:
  `R026_OutIntoTheFolderASessionsLinkedFramesReallySitInIsRefused_Exit1` (a session made only of
  links to its darks, biases and lights, and a partner whose `darks\` is a link: `--out` into
  each real folder, into a folder inside it, and into the folder around the real darks and
  lights; a folder that is none of these is still written, and the linked session is read as
  any other) and `R026_ALinkFarDownALongPathIsFollowedAndADeepFolderHasItsIdentity` (a junction
  moved to a path of over 300 characters, and a session that deep reached through a short link).
- Code, case 1: `DarkOutputs.ReadOnlyFolders` adds, through `AddFrames`, the resolved folder of
  the session's `DarksDir`, `BiasesDir` and `LightsDir` and of a partner's `darks\`, with the
  folder around a real `darks` or `lights` folder; a folder already listed is not added again.
- Code, case 2: `FolderIdentity.Open` hands `CreateFileW` a path of 248 characters or more in
  the `\\?\` form (`Extended`), the length at which .NET's own folder calls switch; tested on
  its own in `R026_ALongPathIsOpenedInTheFormThatTakesIt`.
- The refusals keep their texts. For a linked folder the refusal names the folder the frames
  really sit in, under the words "the session's folder" (or the partner's, the chosen lights').
- Documents: a dated note on ADR 0069 (the two holes its Consequences name are closed), the two
  design notes, a CHANGELOG line, the entry closed in the review list.

## Verification

## The review (2026-11-20)

A subagent review of the branch at the owner's word ("Review intai"). It ran the two cases and
their variants against the branch and against a copy of `main`, and a share through
`\\localhost\C$`. No regression, and both holes closed in every variant it ran. What it found,
each seen again here before it was touched:

- One residual of case 1, the same on `main`: only the folders the run read frames from were
  followed. `darkscheck S --lights L --out U\lights` with `S\lights` a link to `U\lights`
  wrote four files among those lights; a `flats\` link and a `biases\` link without a frame
  likewise. Fixed: R-026 says every session subfolder of the three folders, read or not; the
  test `R026_OutIntoTheFolderALinkedSubfolderLeadsToIsRefusedReadOrNot_Exit1` was seen failing
  (`not refused: ...\lights`); `DarkOutputs.AddSubfolders` took the place of `AddFrames` and of
  its four calls.
- Three lines of the fix no test held (each mutation passed all R026 tests): the real folder
  itself, the biases' line, whose folder a linked chosen lights' refusal names.
  `R026_OutIntoALinkedFolderOfAnotherNameIsRefusedForWhoseItIs_Exit1` holds them now (darks
  linked from a folder of another name, biases linked from a folder of their own, a chosen
  folder whose `lights\` is a link).
- Sentences that said more than the code did: "an ordinary session adds none" (it listed its
  three subfolders; true now, a subfolder that is where its path says is skipped), "none twice"
  in a `<returns>`, and 248 as "the length .NET's own folder calls switch at" (they switch at
  260; 248 is Windows' limit for making a folder by its plain path). Corrected.
- Left as it is, said in the ADR's note: a link named `darks` in the middle of a chain keeps
  the last folder clear and not the folder around the middle link, where no frame sits.

## The second review (2026-11-20)

A subagent review of that fix alone, at the owner's word ("Review pe reparatie"). It printed
the list of protected folders before and after the commit for 38 folder layouts and ran whole
console runs. On NTFS with junctions every outcome is the same as before the commit or a
refusal the commit meant. What it found:

- Two fallbacks the commit had dropped against the first fix (not against `main`), each shown with
  the system's answer stubbed: the early exit `real == sub` took out the entry that tells a
  linked subfolder by its identity when the system cannot name its target, and the real path
  of a library or of a bare folder of chosen lights reached through a link was no longer
  listed. Fixed: `AddResolved` lists each of the three folders and each of its session
  subfolders by its real path, link or not. The test
  `R026_TheListHoldsEachFolderAndItsSubfoldersByTheirOwnPathsAndTheirRealOnes` was seen failing
  on the first of them.
- Whose folder a refusal names had changed in four cases where a session's subfolder leads
  into the partner's or the chosen lights' folder (both names true). The folders as given come
  first again, as before the commit; the same test holds it.
- A mutation that survived: the biases and the flats made to stand for the folder around them.
  The same test holds it now; the comment of an assertion that claimed to was corrected.
- Not from this branch, the same on `main`, entered in the review list: CR-081 and CR-082.
