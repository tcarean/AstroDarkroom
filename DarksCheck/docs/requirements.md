# Requirements

The source of truth for behaviour. Code follows this file, not the reverse. A behaviour change is
first an edit here (status `draft`), then a test, then code (status `implemented`).

Rules for entries:

- IDs are `R-NNN`, assigned once, never reused. A dropped requirement keeps its ID with status
  `dropped`. Gaps in the numbering are deliberate: each block of ten is one area, with one
  exception from the first days, R-008 to R-012 (reading frames, the repository) numbered on
  from the console's block. A full block continues in the next free block of ten, which the
  area's heading then names: the console block R-001 to R-007 is full, so its next requirement
  takes R-080 and the heading says so.
- Status is one of `draft`, `accepted`, `implemented`, `dropped`. `implemented` means a test named
  `R###_...` exists in a test project under `tests/` (`RepoInvariantTests` checks it both ways; it
  reads the sources of the projects it cannot reference).
- Describe observable behaviour, with one concrete example that includes numbers. No adjectives.
- Error behaviour and the exit code are requirements too.

The explanations behind each row (why this way, what was measured) are in `docs/design/` and
`docs/decisions/`; the user documentation of the same behaviour, in English, is `README.md`.
The nine checks of the plan (`docs/plans/2026-10-11-build-darkscheck.md`) map to the areas:
check 1 is the console contract and inventory block below; checks 2 to 8 take the blocks from
R-020; check 9 and the index take the blocks from R-050; the window is the block from R-070.

## The dark series (checks 2 to 8)

The method is the Python prototype's (`prototype/analyze_darks.py`, `supplementary.py`); every
constant is in `Thresholds.cs` (`Th`), the mechanics in `docs/design/dark-analysis.md`
(ADR 0007). Figures are in ADU above black; "ADU-eq" is ADU divided by the normalisation
factor ISO / 400 x exposure / 120 s (ADR 0004), so every threshold is the same whatever the
settings; at ISO 400 and 120 s the two are the same.

| --- | --- | --- |
| R-020 | implemented | The darks are decoded into memory as 16-bit mosaics (the first file sets the size; a file of another size is listed with `dimensiune diferita` and left out); the scale is the file's (libraw's black and white for a raw) and, for a FITS, which carries no black level, the black is the median of the first bias' reference plane when there are biases, else of the first dark's (`negru 200 estimat din mediana cadrului 1`). For each of the four CFA positions of each frame, named from the file's colour order (`R`, `G1`, `G2`, `B`): the median, the clipped sigma (every k-th value so at most 3 million are read; the population std, then three passes dropping what lies over 5 sigma, at least 5 ADU, from the running centre), the mean, the 99.9th percentile, the counts above 10, 20, 50, 100 and 500 ADU-eq (a level is never under `Th.MinHotAdu`, 5 raw ADU, so a short or low-ISO series does not count noise as hot), the saturated (at white - 1 or above) and the dead (below black - 50 raw ADU: a dead pixel does not respond, so it does not scale), the minimum and maximum. A frame whose ISO differs from the first file's, or whose exposure differs by more than 2 %, each setting on its own (ISO 800 at 60 s is not ISO 400 at 120 s), is listed with `setari diferite de primul cadru` and left out; a float FITS on 0 .. 1 is brought to 0 .. 65535, one already in ADU is kept with 65535 as the presumed white, and the saturation of a FITS is read at the file's white, so a 12-bit camera's clipping inside a 16-bit FITS is not seen. The quantisation step is the smallest spacing between the values the first frame takes from black - 10 to black + 30 (2 on a D3300 NEF). Example: six synthetic darks of noise 3 with five hot pixels at 15, 30, 60, 150 and 600 ADU read sigma 2.6 .. 3.4 per plane and master counts 5 / 4 / 3 / 2 / 1 at the five levels. |

## The diagnostic log

The diagnostic log beside each executable, for bug reports (ADR 0025, after FlatCheck's ADRs
0070 and 0072 and LightsCheck's ADR 0029); the mechanics in `docs/design/logging.md`.

| R-100 | implemented | Each application writes a plain-text log, UTF-8 without a byte order mark, in a folder `log` beside its executable, or in `%LOCALAPPDATA%\DarksCheck\log` when that folder cannot be created or written or its newest file cannot be opened for writing (the run's first line says which).
