## Steps (one commit per entry, requirement and failing test first)

Each step: requirement text in `docs/requirements.md`, the failing test (seen red), the fix, the

### 1. CR-013: the pair line is shortened before the two values

- R-054 (now `accepted`) gains the order in which the bar gives up room on a narrow window: the
  hint, then the memory, then the pair line, trimmed with an ellipsis; the coordinates and the
  two values are whole for as long as the room left of the version and the copyright holds them
  (400 DIPs), B the last to go. Example: a window 960 wide with the padded pair of R-050. The
  row becomes `implemented`, since its test is named `R054_…`.
- Tests in `MainWindowTests` (the window never shown, its root laid out at a width, as
  `R022_TheSurfaceStartsAndEndsOnWholePhysicalPixels` does; the texts set on the named
  `TextBlock`s; a helper that walks the layout clips for an item's visible width):
  `R054_OnANarrowWindow_ThePairLineIsShortened_AndTheValuesStayWhole` (client 1008, 944, 784)
  and `R054_OnAWideWindow_TheBarIsLaidOutAsBefore` (1920: every item whole, in the order pair,
  cursor, A, B, memory, hint, each starting where the one before ends).
- Fix in `src/ImageVisualCompare.Wpf/MainWindow.xaml` only, no arithmetic: the left
  `StackPanel` becomes a `DockPanel` holding `StatusAfter`, `StatusBefore`, `StatusCursor`
  docked right in that order and `StatusPair` last, filling, with
  `TextTrimming="CharacterEllipsis"`; `StatusMemory` follows it in the outer `DockPanel`,
  docked left, before the hint. On screen the order is unchanged.
- **ADR 0060** "On a narrow window the status bar shortens the pair line before the two values",
  with the table above and the alternative rejected (the values first, left of the pair line).
  `docs/design/shell.md` gains a section on the status bar's layout. `README.md`, "The status
  bar": one sentence.

### 2. CR-014: Up and Down stay on the surface; a press on the minimap or a bar focuses it

- R-063 gains: `↑` and `↓` do nothing on the surface and leave the focus there; a press on
  the minimap or on a scrollbar gives the surface the focus, as a press on the image does.
- Tests in `MainWindowTests`: `R063_UpAndDown_AreTakenByTheSurface` (a key-down of each raised
  on the surface is handled) and `R063_APressOnTheMinimapOrAScrollbar_FocusesTheSurface` (a
  mouse-down routed through the surface to the minimap, and to a bar; the window's logical
  focus is the surface).
- Fix in `src/ImageVisualCompare.Wpf/Controls/CompareView.xaml.cs`: `OnKeyDown` takes `Key.Up`
  and `Key.Down` with a comment saying why; `Focus()` moves from `OnMouseLeftButtonDown` to an
  `OnPreviewMouseLeftButtonDown` override, which sees the press before the minimap or a thumb
  handles it. `docs/design/shell.md`, "The focus after a toolbar click".

### 3. CR-015: a right click on a scrollbar opens nothing

- R-043 gains: a right click on a bar opens no menu.
- Test in `CompareViewTests`: `R043_ARightClickOnAScrollbar_OpensNoMenu` (`ContextMenuOpening`
  raised on each bar, its event arguments built by reflection as `Press` builds a repeat; the
  bar's `ContextMenu` is null after it).
- Fix in `src/ImageVisualCompare.Wpf/Theme.xaml`: `ContextMenu` set to `{x:Null}` in
  `ThinVerticalScrollBar` and `ThinHorizontalScrollBar`, with a comment (WPF puts its stock
  menu only where the property is at its default). The summary of
  `CompareView.OnScrollBarMoved` loses "clicking it, or its context menu" (a line of CR-028,
  noted there).
- **ADR 0061** "The scrollbars have no context menu", with the alternative rejected (a dark
  menu worded by `UiText`). `docs/design/rendering.md`.

### 4. CR-016: the keyboard focus is an accent border, never a dotted rectangle

- New **R-068**: the button that has the keyboard focus has the accent border; in a dialog the
  default button has it while no button has the focus, since Enter then answers with it, and
  loses it when another button takes the focus; a link that has the focus is underlined, as
  under the pointer; WPF's dotted rectangle is drawn nowhere, neither on a button nor over the
  comparison surface.
- Tests in a new `ThemeFocusTests` (on `WpfThread`): `R068_AButtonWithTheKeyboardFocus_
  HasTheAccentBorder` (theory over `ToolButton`, `ToolToggleButton`, `ChangeButton`,
  `DialogButton`: the template's border before and after the read-only focus property is set
  through its key, by reflection), `R068_TheDefaultDialogButton_IsLitOnlyWhileEnterAnswersWithIt`,
  `R068_NoDottedRectangle_OnAButtonOrOverTheSurface` (`FocusVisualStyle` null). If the property
  key cannot be reached, the tests assert the template's trigger instead, and the plan's
  deviations say so.
- Fix: `Theme.xaml`: `FocusVisualStyle` null and a template trigger on `IsKeyboardFocused` (the
  accent border) in `ToolButton` and `ToolToggleButton`; `DialogButton`'s trigger on `IsDefault`
  becomes one on `IsDefaulted`; the `Hyperlink` style gets `FocusVisualStyle` null and the
  underline on `IsKeyboardFocused`. `Controls/CompareView.xaml`: `FocusVisualStyle="{x:Null}"`.
  One visible change beside the fix: a dialog that is not the active window lights no button,
  as Windows' own dialogs do.
- **ADR 0062** "The keyboard focus is shown by the accent border, never by WPF's dotted
  rectangle" (it follows ADR 0018). `docs/design/shell.md`.

### 5. CR-017: a file whose size changed since its header was read is refused

- R-005 gains the case: a file whose decoded size is not the size its header gave when the
  canvas was settled gives `Could not read <file name>.` and the new line below. R-009 gains:
  the same for the new file, and for the kept image when it is decoded again.
- New text, `UiText.FileChangedOnDisk` (no text exists today):
  - English: `The file has changed on disk: it was 5938 × 3888, it is now 4000 × 3000. Open the pair again.`
  - Romanian: `Fișierul s-a schimbat pe disc: era 5938 × 3888, acum este 4000 × 3000. Deschide din nou perechea.`
- Tests in `ImagePairLoaderTests`, with a fake loader that decodes a size other than the one it
  probed: `R005_AFileWhoseSizeChangedSinceItsHeaderWasRead_IsRefused` (A, then B, in
  `LoadAsync`), `R009_AKeptFileWhoseSizeChangedOnDisk_IsRefused_NotShownOnTheOldCanvas` (the
  review's case: a mode that falls to `Linear` decodes the kept file again) and the same for the
  new file; `UiTextTests`: both wordings.
- Fix in `src/ImageVisualCompare.Wpf/Imaging/ImagePairLoader.cs`: a private `EnsureSize` called
  after each of the four decodes, which throws an `IOException` carrying the text when the
  decoded `ImageInfo` differs in width or height from the one the `PadPlan` was made from; the
  existing `Failed` path words, logs and returns it. Nothing in `MainWindow` changes: a failed
  open asks again, a failed change or mode switch leaves the pair on screen.
- **ADR 0063** "A file whose size changed between its header and its decode is refused", with
  the alternative rejected (plan again and ask again). `docs/design/imaging.md`. `README.md`:
  a sentence where the messages of a file that cannot be read are listed, if they are.
