## What was measured before the plan (2026-11-14, throw-away tests, removed again)

- **CR-004, confirmed.** A float RGBA TIFF with `ExtraSamples = 1` is reported by WIC as
  `Prgba128Float`. Converted to `Rgba128Float`, as `LoadFloat` asks, the colours are divided by
  alpha: stored (0.2, 0.2, 0.2, alpha 0.5) loads as level 102, not 51; stored 0.3 at alpha 0.25
  loads white; at alpha 0 the colours become 0. Asked for as `Prgba128Float`, the four floats
  arrive as stored.
- **CR-005, confirmed.** An 8-bit PNG pixel (200, 200, 200, alpha 128) loads as those bytes, is
  drawn at 100 over the black backdrop, and is read as `200 200 200`. Same for a 16-bit RGBA PNG
  and an indexed PNG with transparent entries. A conversion through `Bgr32` and on to `Bgra32`
  gives the same colour bytes with alpha 255. On the three real files (`de_printat.png`, the
  16-bit TIFF, the 8-bit TIFF) it costs the same time and memory as today within the noise of
  two runs (5.6 to 6.9 s against 5.6 to 6.3 s; +87 to +91 MiB both ways), and sampled rows are
  byte-identical.
- **CR-007, confirmed in the arithmetic; nothing differs on the real files.** Siril 1.4
  (`core/proto.h`, `io/image_formats_libraries.c`, read on GitLab) turns a float into 16 bits as
  `(WORD)(f * 65535f + 0.5f)`, all in single precision, for its display and for its 16-bit PNG
  and TIFF exports. Over every float from 2^-17 to 1: the 16-bit value differs from this
  program's for 32,767 floats (Siril's always one higher), and the level for 127, all in
  [0.5, 1). On the five float FITS of `Processed_WithFlats_RBF_light` (69,260,832 samples each):
  18 to 2,564 16-bit values differ, no level.
- **CR-003 and CR-006: not measured on screen.** The owner was at the PC and chose "nothing on
  screen now". CR-003's confirmed part (an empty folder for the dialogs) and CR-006's mechanism
  (`SetCursorPixel` drops an unchanged pixel; `OnMouseMove` returns before the read-out during a
  drag) follow from the code and get failing tests. Whether the Windows dialog moves the current
  folder, and the case with the mouse button held, stay unmeasured; the fixes do not depend on
  them, and the list will say so.

### 1. CR-003: a pair named by relative paths is held by its full paths

- R-002 gains: a relative path is taken against the folder the program was started in, once, at
  start-up, and the pair is held by its full paths from then on.
- Test `R002_APairNamedByRelativePaths_IsHeldByItsFullPaths` (in `LoggingTests`, the collection
  that already serialises `App.ApplyCommandLine`): two files in a new folder under the current
  folder, named relatively; the selection's paths are rooted and equal the full paths.
- Fix in `App.ApplyCommandLine` (`src/ImageVisualCompare.Wpf/App.xaml.cs`): `Path.GetFullPath`
  on both, after the `File.Exists` checks, before the selection and the log line.
  `docs/design/language.md` (covers the command line) gets the sentence.

### 2. CR-004: a float TIFF with associated alpha is read as stored

- R-091 gains: a file whose alpha is associated (WIC's `Prgba128Float`) is asked for in that
  format, so its colours arrive undivided.
- `TempImages.WriteFloatTiff` gains an optional `associatedAlpha` (tag 338 = 1; default as today).
  Test `R091_AFloatTiffWithAssociatedAlpha_IsShownAsStored_NotDividedByAlpha` in
  `WicImageLoaderTests`: the four pixels measured above, levels 51 / 76-25-12 / 153 / 25-51-76.
- Fix in `WicImageLoader.LoadFloat`: target `Prgba128Float` when the frame is; the stale comment
  ("between float formats WIC copies the values") corrected. `docs/design/imaging.md`.

### 3. CR-005: no transparency; every image is opaque

- R-010: "converted to Bgra32 with alpha 255: transparency is not shown, a pixel's stored colours
  are drawn and read whatever its alpha". R-051 names it in one clause.
- Tests in `WicImageLoaderTests`: `R010_ATransparentPixel_IsLoadedOpaque_WithItsStoredColours`
  (8-bit RGBA PNG, 16-bit RGBA PNG, indexed PNG with transparent entries: colour bytes kept,
  alpha 255), and that an opaque RGB file loads to the same bytes as before.
- Fix in `WicImageLoader.Load`: the frame converted to `Bgr32`, then to `Bgra32`, both lazy, one
  realisation as today. No branch on the format.
- **ADR 0054** "No transparency: every image is shown opaque", superseding in part ADR 0013
  (its consequence that transparency shows over black; the backdrop stays, for the padding).
  ADR 0013's status line gets the "superseded in part by 0054" clause, as 0052 has for 0053.
  `docs/design/rendering.md` (the backdrop paragraph) and `imaging.md`; noted there as measured:
  a TIFF with associated integer alpha reaches us already divided by WIC's decoder.
- `README.md` if it speaks of transparency. The wiki manual says PNG and TIFF open "with or
  without transparency": the new sentence is shown to the owner, original and proposal, and
  changed in the wiki clone only at the owner's word (another repository).

### 4. CR-006: the read-out follows what is under a resting pointer

- R-051: "The readout changes when the pointer reaches another whole pixel, and when what is
  under a resting pointer changes: the pair, the display mode, the zoom or the pan."
- Tests: `MainWindowTests.R051_TheReadOut_FollowsAModeSwitchUnderARestingPointer` (a fake loader
  whose bitmap value depends on the mode; `ReportPointer` once, `ToggleModeAsync`, the status
  texts must change with no second report) and the same for `ChangeImageAsync`;
  `CompareViewTests.R051_AZoomUnderARestingPointer_ReportsThePixelNowUnderIt`.
- Fix in `CompareView` (`Controls/CompareView.xaml.cs`): keep the pointer's last position
  (set in `OnMouseMove` before the drag branches and in `ReportPointer`, cleared in
  `OnMouseLeave`); `Sync` reports the pixel now under it (null when the position is outside the
  surface, as during a captured drag); `SetPair` and `ReplacePair` raise `CursorPixelChanged`
  even for the same pixel, since the bitmaps under it changed. `MainWindow.ShowPair` already
  sets `_pair` and `_mode` before it hands the pair to the surface, so its handler reads the new
  pair. No arithmetic in the control: the pixel is still `Viewport.PixelAt`'s.
  `docs/design/rendering.md` ("The read-out names the pixel that is drawn").

### 5. CR-007: a float sample is quantised in single precision, as Siril does

- R-015 says the precision: for a float sample, `(ushort)(f × 65535 + 0.5)` computed in single
  precision as Siril 1.4 computes it for its display and its 16-bit exports; a float file read
  as 0 to 65535 is first brought to 0 to 1 in single precision, as Siril does on reading it
  (`data × (1/65535)`). Example: 0.8359426259994507 shows 214, where double gave 213. R-091
  follows through R-015. The exact value of Siril's `INV_USHRT_MAX_SINGLE` is read in its
  source first.
- Tests: `FitsScaleTests.R015_AFloatSample_IsQuantisedInSinglePrecision_AsSirilDoes` (the two
  floats of the entry; over [0.5, 1) the counts measured above, 16,384 and 127);
  `FitsRowDecoderTests` and `FloatSamplesTests`, one case each through the float path.
- Fix: `FitsScale` (Core) gains the single-precision `SixteenBit` for float samples;
  `FitsRowDecoder` (BITPIX -32 and -64, after BZERO and BSCALE, cast to float as cfitsio hands
  them to Siril) and `FloatSamples.ToSixteenBit` call it. Integer FITS keep the double path,
  which is exact for them. The comment on the double `SixteenBit` that says Siril does the same
  is corrected.
- **ADR 0055** "A float sample becomes 16 bits in single precision, as in Siril", with the source
  read and the counts. `docs/design/imaging.md`.
- An existing test that fails because of the new rule is not edited: stop and report it.
