# Requirements

The source of truth for behaviour. Code follows this file, not the reverse. A behaviour change is
first an edit here (status `draft`), then a test, then code (status `implemented`), and the design
note of its area changes in the same task (the kit's rules "Requirements first" and "Design
notes"). Until 2026-10-02 the behaviour was described only by the code, its comments and the user
documentation; that day `CLAUDE.md` was split into this file, `docs/decisions/` and `docs/design/`
(ADR 0001).

Rules for entries:

- IDs are `R-NNN`, assigned once, never reused. A dropped requirement keeps its ID with status
  `dropped`. Gaps in the numbering are deliberate: each block of ten is one area.
- Status is one of `draft`, `accepted`, `implemented`, `dropped`. `implemented` means a test
  named `R###_...` exists in `tests/ImageVisualCompare.Tests` (`RepoInvariantTests` checks it both
  ways). `accepted` means the behaviour is agreed and in the code, and no test carries the ID yet.
  On 2026-10-02 that is the WPF layer (R-001, R-002, R-008, R-050 to R-054, R-060 to R-063),
  which had no tests by design and is checked by launching the application (ADR 0026), and the
  memory figures (R-080, R-081), which the cases of `docs/validation.json` guard outside the gate.
  Since 2026-10-22 a defect reproduced on a window or a control gets a test on the WPF test
  thread (ADR 0032), under the ID of the behaviour it breaks.
- Describe observable behaviour, with one concrete example that includes numbers. No adjectives.
- Error behaviour is a requirement too.
- Constants are quoted by their name in the code and their value on 2026-10-02; the code holds the
  value, this file the meaning.
- The examples use the README's controls and status bar, and the real pairs of
  `docs/validation.md`: `de_printat.png` and `de_printat_PRINT_preview_16bit.tif` (both
  5938 × 3888, 16-bit RGB), and `de_printat_50x35_TIFF8.tif` (5554 × 3888, 8-bit RGB).

The user documentation of the same behaviour, in English, is `README.md` (ADR 0025, ADR 0041);
the explanations behind each row are in `docs/design/` and `docs/decisions/`.

## Opening a pair

| ID | Status | Requirement |
| --- | --- | --- |
| R-001 | accepted | Without paths on the command line, the application asks for the two images with two Windows open dialogs in turn, titled `Select image A  —  shown left of the divider` and `Select image B  —  shown right of the divider`; the filter's entries are `Images (*.png;*.tif;*.tiff;*.fit;*.fits;*.fts)` (the default), `PNG (*.png)`, `TIFF (*.tif;*.tiff)`, `FITS (*.fit;*.fits;*.fts)` and `All files (*.*)`. The second dialog opens in the folder of the first file; a later first dialog opens in the folder of the image A chosen last, whether or not that pair loaded. Cancelling either dialog cancels the pair: with no pair loaded the application closes, with one loaded it stays as it was. Example: picking `E:\Photografie\Claude\de_printat.png` as A opens the B dialog in `E:\Photografie\Claude`. |
| R-002 | accepted | Two or more arguments, `--lang` and its value aside (R-100), whose first two name existing files skip the dialogs: the first is image A, shown left of the divider, the second image B. The pair from the command line is used once; `Ctrl+O` and `Open…` go through the dialogs afterwards. Fewer than two arguments, or a path that does not exist, fall through to the dialogs, not to an error. Example: `ImageVisualCompare.Wpf.exe "A.png" "B.png"`. |
| R-003 | implemented | Both headers are read (`IImageLoader.Probe`) before any pixel is decoded. When the pixel dimensions differ, the user is asked first, in the dialog titled `Images have different sizes`, with the text of `ImagePairValidator.DescribeMismatch`: `The two images have different dimensions.`, `A: <file name> — <W> × <H>`, `B: <file name> — <W> × <H>`, a blank line, `Both can be padded with black to <W> × <H>,`, `anchored top-left, and compared on that canvas.`, `The image files themselves are not modified.`, a blank line, `Continue?`. `Yes` loads the pair (R-004); `No` returns to the dialogs with no message and nothing decoded. With no one to ask (`confirmPadding` null) the same text comes back as the error and nothing is decoded. A pair of equal dimensions is never asked about. Example: `de_printat.png` (5938 × 3888) against `de_printat_50x35_TIFF8.tif` (5554 × 3888) asks to pad both to `5938 × 3888`. |
| R-004 | implemented | The canvas a pair is compared on is the larger extent on each axis (`ImagePairValidator.Inspect`, `PadPlan`), and `RequiresPadding` is true when the two dimensions differ. Both images are drawn at their own pixel size from the top-left corner of the canvas; where one does not reach, the black backdrop shows; neither image is copied, moved or resized. Example: 5938 × 3888 against 5554 × 3888 gives a 5938 × 3888 canvas with `RequiresPadding` true, and image B ends 384 pixels before the right edge. |
| R-005 | implemented | A file that is missing, locked, truncated, in a format no codec reads, or too large for the machine (`IOException`, `UnauthorizedAccessException`, `NotSupportedException`, `FileFormatException`, `ArgumentException`, `OutOfMemoryException`) gives the message `Could not read <file name>.` and, on the next line, the exception's message, shown in the dialog titled `Cannot compare these files`; then the dialogs open again. WIC's own failures arrive as those types (ADR 0031): an image too large to decode, which WIC fails with an `OverflowException`, as `An image of <W> × <H> is too large to show.`, and a file its codec rejects with a `COMException`, such as a damaged WebP, HEIC or AVIF, with the codec's message. It never crashes the application; a cancellation is not a failure and is passed on. Example: a corrupt `broken.png` gives `Could not read broken.png.` followed by the codec's message; a PNG whose header says 40 000 × 30 000 gives `Could not read huge.png.` and `An image of 40000 × 30000 is too large to show.` |
| R-006 | implemented | While a pair loads, an overlay over the whole window shows `Opening…`, then `Decoding <file name>…` for each image, then `Almost there…`, over a progress bar fed by `ImageLoadProgress`: 0 with A's file name, 0.5 with B's, 1 with no name. The two images are decoded one after the other, never at the same time. The overlay is hidden while the question of R-003 is on screen. While a pair is being opened, from its file dialogs to the pair on screen or the message of R-005, `Ctrl+O` and `Open…` do nothing, so a second pair is never asked for or decoded on top of it; the overlay stops only the mouse (ADR 0036). Example: `Ctrl+O` pressed while `Decoding de_printat.png…` shows opens no dialog. |
| R-007 | implemented | A loaded pair (`ImagePair`) holds both images, the canvas (`PixelWidth`, `PixelHeight`) and `DisplayBytes`, the sum of the two Bgra32 buffers. Example: `de_printat.png` with `de_printat_PRINT_preview_16bit.tif` holds 184 695 552 display bytes (2 × 92 347 776) on a 5938 × 3888 canvas. |
| R-008 | accepted | Once a new pair has loaded, it takes the place of the current one on the surface, one render pass is let through, and only then are the outgoing pair's buffers released (`MemoryHousekeeping.ReleaseImageBuffers`): until that pass the surface's images still hold the outgoing bitmaps in their render content, and a release before it frees nothing (ADR 0040). While the new pair decodes, the current one is still on screen. The new pair is shown at fit (R-021) with the divider at the centre, and the comparison surface takes the keyboard focus. The window title becomes `<A>  vs  <B>  —  Image Visual Compare <version>` and the toolbar shows `<A>   vs   <B>`, with the file names. Example: `de_printat.png  vs  de_printat_PRINT_preview_16bit.tif  —  Image Visual Compare 1.1.1`. |

## Formats

| ID | Status | Requirement |
| --- | --- | --- |
| R-010 | implemented | PNG and TIFF files in any pixel format WIC decodes are accepted: 8 or 16 bits per channel, gray, RGB, RGBA, indexed, and a TIFF of floating-point samples (R-090). Every image is converted to Bgra32 and frozen, so it can be used from any thread; the file is not locked once loaded; loading off the calling thread gives the same result. Example: a 16-bit RGB PNG exported from Siril loads as a Bgra32 bitmap of the same pixel size. |
| R-011 | implemented | The format reported is the file's own, read with `PreservePixelFormat`, as `WicImageLoader.Classify` maps it and `ImageInfo.FormatDescription` words it: `Rgb48` is `16-bit RGB`, `Bgr24` and `Rgb24` are `8-bit RGB`, `Gray16` is `16-bit gray`, `Gray8` `8-bit gray`, `Indexed8` `8-bit indexed`, `Rgba64` `16-bit RGBA`, `Bgra32` `8-bit RGBA`; a format the table does not know is reported by its bits per pixel, `<n>-bit`, and loaded anyway; a TIFF of floating-point samples is reported as R-090 says. `Probe`, which reads only the header, reports exactly what a full load does, but for the range a float TIFF's load can add (R-091), as a FITS's can (R-018). Example: a Siril "32-bit" export is a PNG with 16 bits per channel (48 bpp), reported `16-bit RGB`. |
| R-012 | implemented | Bit depth and channel layout may differ between A and B; only the pixel dimensions are compared. Example: a 16-bit RGB PNG against an 8-bit RGB TIFF of the same size loads without a question. |
| R-013 | implemented | `ImageInfo.DisplayBytes` is width × height × 4, the Bgra32 footprint; `Dimensions` is `<W> × <H>` with the multiplication sign; `FileName` is the name without its folder. Example: `de_printat.png` gives 92 347 776 display bytes and `5938 × 3888`. |
| R-014 | implemented | A FITS file is accepted as image A or B. A file is FITS when its first nine bytes are `SIMPLE  =` (`FitsHeader.IsFits`), whatever its extension; every other file goes to WIC as before (`RoutingImageLoader`). The image is the first header-data unit that holds one: the primary, or an `IMAGE` extension, with 2 axes, or 3 axes whose third is 1 or 3 planes; an empty primary, a table and random groups are skipped by the size their header gives (a unit with no axes, `NAXIS` 0, has no data at all, whatever its `PCOUNT`), and bytes after the last unit that are not an extension end the search. `BITPIX` 8, 16, 32, -32 and -64 are read, with `BZERO` and `BSCALE` applied. Three planes are red, green and blue; one plane is shown gray (R = G = B), a colour filter array is not demosaiced. The result is a frozen Bgra32 bitmap with alpha 255, and the file is not locked once loaded (as R-010). Example: `result_3813s.fit` from Siril 1.4.4, three planes of 32-bit float, 5938 × 3888, loads as a 5938 × 3888 Bgra32 bitmap. |
| R-015 | implemented | FITS values are shown linearly, with no stretch: a value is divided by the full scale of its type (`FitsScale.FullScale`: 255 for `BITPIX` 8, 65 535 for 16, 4 294 967 295 for 32, 1 for float unless R-016 applies), brought to 16 bits (`round(value × 65535)`), and reduced to 8 bits as WIC reduces a 16-bit PNG, by keeping the high byte (`FitsScale.ToByte`; WIC's rule measured on all 65 536 values on 2026-10-05). The same samples written as a 16-bit FITS and as a 16-bit RGB PNG therefore load to the same Bgra32 bytes. Example: the float 0.5 is 32 768 of 65 535 and shows as 128; 255 / 65535 shows as 0 and 256 / 65535 as 1. |
| R-016 | implemented | A float FITS is read as 0 to 1 unless more than `FitsScale.RescaleFraction` (0.01, one in a hundred) of its samples, all planes, are finite and above `FitsScale.RescaleThreshold` (2.0), in which case the whole file is read as 0 to 65 535 and decoded again with that full scale. A share and not one sample: a hot pixel above 2 in a file in 0 to 1 leaves the file in 0 to 1. NaN and values below 0 show as 0; values above the full scale show as 255. Example: a float file in 0 to 65 535 shows the sample 41 200 as 160 (41 200 of 65 535 is 0.6287); a 20 × 10 file at 0.5 with one sample at 2.5 shows 128 everywhere and 255 at that sample; `result_3813s_wcsplane_bge.fit`, whose largest sample is 1.0005, is read as 0 to 1. |
| R-017 | implemented | The first row in the file is the bottom row of the image, whatever `ROWORDER` says: Siril, the display the tool is compared against, reads and shows every FITS bottom-up and uses the keyword only for the Bayer pattern (ADR 0039). Example: a 2 × 2 file whose first sample is 1.0 and the other three 0 shows white at the bottom left, with `ROWORDER = 'TOP-DOWN'` as without the keyword. |
| R-018 | implemented | For a FITS the format reported (`ImageInfo.FormatDescription`, R-011) is its depth and planes: `8-bit`, `16-bit` or `32-bit` for integers, `32-bit float` or `64-bit float` for floats, then `gray` for one plane and `RGB` for three; a float file read as 0 to 65 535 (R-016) adds ` (0..65535)`. `Probe` reports the size, the depth and the planes of the load; the scale is known only after the decode, so only the loaded image says it. Example: `32-bit float RGB`; `32-bit float gray (0..65535)`. |
| R-019 | implemented | A FITS that cannot be shown gives the message of R-005, `Could not read <file name>.` and a line of its own, and nothing is decoded: `FITS: no image found in the file.`; `FITS: an image with <n> axes is not read; 2, or 3 with 1 or 3 planes, are.`; `FITS: an image with <n> planes is not read; 1 or 3 are.`; `FITS: BITPIX <n> is not read.`; `FITS: a tile-compressed image is not read.` (an extension with `ZIMAGE = T`); `FITS: the header is not valid.` (a negative axis, `PCOUNT` or `GCOUNT`, one that is not an integer, more than 999 axes, sizes whose product does not fit 64 bits, or a `BZERO` or `BSCALE` that is NaN or infinite, as `NaN` and `1D999` are); `FITS: an image of <W> × <H> is too large to show.` (a width over 268 435 455, a data size that does not fit 64 bits, or more pixels than a bitmap holds); `FITS: the header ends before its END card.`; `FITS: the file ends before the image data does.` The last is found by `Probe`, from the file's length. No header makes the reader loop or crash: a header is not trusted. Example: a file cut to its first 10 000 bytes gives `FITS: the file ends before the image data does.` |

## Zoom and pan

| ID | Status | Requirement |
| --- | --- | --- |
| R-020 | implemented | The zoom floor is `Viewport.MinScale`: the fit scale, at which the whole image is visible, or 1 (100 %) when the image is smaller than the viewport, so a small image can still be seen at its own resolution. The ceiling is `Viewport.MaxScale`, 16 (1600 %). A zoom outside the two is clamped. Example: a 5938 × 3888 image in a 2969 × 1944 physical-pixel viewport cannot go below 50 %; a 1000 × 800 image in the same viewport cannot go below 100 %. |
| R-021 | implemented | `Fit` (the button, `Ctrl+0`, and every new pair) zooms to the fit scale, clamped to the floor and the ceiling, and centres the image on the axis with room to spare, with equal empty margins; an axis the image does not fill is always centred. Example: a 5938 × 3888 image in a 2969 × 2000 viewport fits at 50 % with 28 empty physical pixels above and below. |
| R-022 | implemented | `100%` (the button and `Ctrl+1`) is one image pixel per physical screen pixel, anchored at the viewport centre. The viewport counts in physical pixels, and the render scale is `Viewport.Scale / deviceScale` with the translation `-OffsetX`, `-OffsetY` (`RenderPlanner.For`). A device scale of zero or less is rejected with `ArgumentOutOfRangeException`. This holds on every monitor, whatever its own scaling: the application declares per-monitor DPI awareness (`PerMonitorV2` in its manifest, ADR 0034), so the device scale is that of the monitor the window is on, read again when the window moves to another. Example: on a display scaled to 150 %, an image at 100 % is drawn at a render scale of 0.667, one physical pixel per image pixel, also when the main display is at 100 %. |
| R-023 | implemented | The mouse wheel zooms by `WheelZoomFactor` (1.15) per wheel event, in or out, anchored at the cursor: the content point under the pointer stays under it. `Ctrl`+wheel does the same. `Shift`+wheel pans horizontally by `WheelPanPixels` (140 physical pixels) per wheel event. Example: three notches in from 100 % give 152 % (1.15³ = 1.521). |
| R-024 | implemented | `+` and `−` (the keys `OemPlus`, `Add`, `OemMinus`, `Subtract`, and the toolbar buttons) step to the next or the previous stop of `ZoomLadder.Steps`: 0.02, 0.03, 0.05, 0.08, 0.125, 0.17, 0.25, 0.33, 0.5, 0.67, 1, 1.5, 2, 3, 4, 6, 8, 12, 16, anchored at the viewport centre and clamped like any zoom (R-020). A scale between two stops steps to its neighbour (stops within 1e-6 of the scale do not count); past the top the step stays at the top. `−` never zooms in: when no stop is below the scale, which happens only when the window is so small that the fit is under 2 %, it goes to the floor (R-020), and at the floor it does nothing (ADR 0033). Example: at 152 % after a wheel zoom, `+` goes to 200 % and `−` to 150 %; a 5938 × 3888 image in a 91 × 60 physical-pixel viewport fits at 1.53 %, and `−` from 1.8 % goes to 1.53 %, not up to 2 %. |
| R-025 | implemented | From `RenderPlanner.PixelatedThreshold` (4.0, that is 400 %) up, both images are resampled nearest-neighbour, so each image pixel shows as a square; below it they are resampled with `HighQuality`. Example: at 399 % the image is smooth, at 400 % its pixels are squares. |
| R-026 | implemented | Dragging with the left button outside the divider pans the images with the pointer; the offset is clamped so an image larger than the viewport cannot be dragged past its edges (`Viewport.MaxOffsetX`, `MaxOffsetY`), and an axis the image fits stays centred. The scrollbars and the minimap set the offset through the same clamp; `CentreOn` puts a content point in the middle of the view. Example: at 100 % a 5938 px wide image in a 2969 px wide viewport scrolls horizontally from offset 0 to 2969. |
| R-027 | implemented | When the window is resized, the content point at the centre of the view stays at the centre, and the scale is clamped again, so growing the window raises the fit scale and pulls a zoom that sat at the old floor up to the new one. |
| R-028 | implemented | The image pixel under the cursor (`Viewport.ContentPointInsideAt`) is the content point at the pointer's physical position, or null on the empty margin around the image, at the far edge (x equal to the width has no pixel) and when nothing is loaded. |
| R-029 | implemented | With nothing loaded, zoom and pan do nothing; a negative content or viewport size is rejected with `ArgumentOutOfRangeException`; converting a screen point to content and back returns the same point. |

## The divider

| ID | Status | Requirement |
| --- | --- | --- |
| R-030 | implemented | The divider is a vertical line at a fraction of the viewport width (`DividerModel.Position`: 0 at the left edge, 1 at the right), clamped to 0..1; it starts at 0.5 and is reset to 0.5 for every new pair. It belongs to the window: zooming and panning move the images under it and leave it where it is. Image A is shown left of it, image B right of it. Example: dragging the line to x = 500 on a 2000 DIP wide surface sets the position to 0.25; after the window shrinks to 1000 DIPs the line is at x = 250. |
| R-031 | implemented | With the comparison surface focused, `←` and `→` move the divider by 1 device-independent pixel, `Shift+←` and `Shift+→` by 10. |
| R-032 | implemented | A left-button press starts a divider drag, not a pan, when it lands within `DividerModel.LineGrabTolerance` (8 DIPs) of the line anywhere along its height, or inside the handle, `HandleWidth` (26) by `HandleHeight` (56) DIPs, centred on the line and on the height. The cursor over the line or the handle is `SizeWE`; while panning it is `SizeAll`. The handle the surface draws is the rectangle the hit test accepts. Example: on a 2000 × 1000 DIP surface with the line at x = 1000, a press at (1012, 500) grabs the handle, a press at (1012, 100) pans. |
| R-033 | implemented | Image A is clipped to the region from the left edge to the line (`DividerLayout.ClipRect`: from 0 to `LineX`, the full height); the line is 2 DIPs wide; the handle is centred on the line and on the height. At positions 0 and 1 the layout stays well formed: an empty clip and a full one. |

## Minimap and scrollbars

| ID | Status | Requirement |
| --- | --- | --- |
| R-040 | implemented | The minimap at the bottom left of the surface shows a thumbnail of the shared canvas, not of image A alone, fitted with its aspect ratio into `MaxThumbnailWidth` (190) by `MaxThumbnailHeight` (150) DIPs (`AspectFit.Fit`; a zero or negative size gives an empty box). The thumbnail bitmap is rendered once per pair from image A, at most 380 by 300 pixels, over black where A does not reach. Example: a 5938 × 3888 canvas gives a minimap of 190 × 124.4 DIPs. |
| R-041 | implemented | On the thumbnail, the viewport rectangle is the visible region scaled to the thumbnail, clamped to the thumbnail where the view overhangs the image, never smaller than 2 DIPs a side (the minimap's own units), and hidden when the whole image is on screen; with nothing loaded nothing is drawn. The thumbnail is the area inside the minimap's 1-DIP border, and the rectangle stays inside it: floored to 2 DIPs at the far edge, it is moved in, not drawn past it. Example: on a 190 × 124.4 minimap the thumbnail is 188 × 122.4, and the 5938 × 3888 pair at 1600 % scrolled to the bottom right ends its rectangle at 188, 122.4. |
| R-042 | implemented | A click in the minimap, or a drag across it, centres the view on the content point under the pointer, measured on the thumbnail inside the minimap's border. Example: a click at the centre of the thumbnail centres the view on the middle of the image; a click on the thumbnail's top-left corner centres it on the image's (0, 0). |
| R-043 | implemented | A scrollbar appears only on an axis the image overflows; its range is 0 to the largest offset, its thumb the visible extent, its value the current offset clamped into the range, and moving it pans the view. The bars float over the image, so their appearing never changes the viewport size. Example: at fit no bar is shown; at 100 % on a 5938 × 3888 image in a 2969 × 1944 viewport both are, each with a range of 0 to 2969 and 0 to 1944. |

## Float TIFF

## Display modes

Siril 1.4.4 is the reference display (ADR 0039, ADR 0040): its "Histogram" display mode and its
rainbow colour map, read in its source at that tag (FlatCheck's `docs/design/siril-histeq-source.md`).

| ID | Status | Requirement |
| --- | --- | --- |
| R-110 | implemented | The pair is shown in one of three display modes, `Linear` (every file as R-010 to R-019 and R-091 say), `Histogram` (R-111) and `FalseColours` (R-112). `Histogram` and `FalseColours` can be asked for only when both files are shown as stored, a FITS (R-015) or a float TIFF (R-091), which `ImageInfo.ShownAsStored` says from the probe on; for any other pair the two buttons of R-114 are disabled, `H` and `F` do nothing, and the pair is `Linear` whatever mode was asked. Example: `result_3813s.fit` against `result_3813s_Graxpert_AI.fit` allows all three modes; `result_3813s.fit` against `de_printat.png` allows `Linear` only. |
| R-111 | implemented | In `Histogram` each channel is equalised on its own histogram as Siril's "Histogram" display does: 65 536 bins on the 16-bit value of R-015 and R-091 (`FitsScale.SixteenBit`, the value whose high byte is the linear level), bin 0 left out of the counts but counted among the pixels, and the lookup `index[0] = 0`, `index[i] = RoundToByte(cumulative(i) / pixels × 255)` with bin `i` included, where `RoundToByte(x) = min(255, (int)(x + 0.5))` (`LevelLookup.RoundToByte`).
