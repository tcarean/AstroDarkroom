### CR-012 A FITS header with an impossible size is refused, not followed

- R-011: the sizes of every HDU are checked before they are used: `NAXIS` between 0 and 999 (the
  standard's range), no `NAXISn` negative, `BITPIX` one of 8, 16, 32, 64, -32, -64 when the HDU
  has data, the data's byte count without overflow; the image's pixels must fit what the tool
  can hold, and its data must be in the file before memory is taken for them.
- `Input/FitsReader.cs`: one member, `Shape(hdr)`, returns the HDU's `BITPIX`, axes, planes and
  data bytes, checked; `LoadFrom`, `ReadImageHeader` and the two walks of `Input/FitsWriter.cs`
  (`FromFits`, `CropFromFits`) all read the sizes through it, so the four copies of the same
  lines become one. `LoadFrom` compares the data's length with the stream's (when it can seek)
  before `new Raster`.
- New texts (the existing `unsupported BITPIX:` and `FITS: truncated data.` are reused):
  - `FITS: the header's NAXIS1 is negative: -2.` / `FITS: NAXIS1 din header e negativ: -2.`
  - `FITS: the header's NAXIS is not between 0 and 999: 2000000000.` /
    `FITS: NAXIS din header nu e intre 0 si 999: 2000000000.`
  - `FITS: the image is too large to read: 50000 x 50000 px.` /
    `FITS: imaginea e prea mare ca sa fie citita: 50000 x 50000 px.`
- Tests `R011_...` in `FitsReaderTests`, each of the entry's five headers through `LoadFrom`
  inside a task with a time limit (the first two hang today, so the test must not): `NAXIS1 = -2`
  in an HDU that is skipped; `NAXIS = 2000000000`; 50000 x 50000; 40000 x 40000 x 3 in a 3 KB
  file (refused as truncated, no allocation); `BITPIX = -2147483648`. The negative axis also
  through `ReadImageHeader` (the `--wcs` route) and through a crop (`FitsWriter`).
  `FitsTestData.WithCard` builds the cards.

### The review of the branch, 2026-11-20

At the owner's word a subagent with a clean context reviewed everything that differs from
`main` (read only; it built nothing). No blocking defect: the five fixes do what their entries
ask on every caller it found. Each finding was opened in the code before anything changed.

Applied, both in the area of CR-012 and both needing a crafted file:

1. An empty primary HDU (`NAXIS = 0`) has no samples, so its `BITPIX` is not checked and the
   reader takes the file; the crop's walk still computed the bytes of a sample for every HDU,
   and `BITPIX = -2147483648` there threw the platform's overflow.
   `R011_AnEmptyPrimaryWithAnImpossibleBitpixIsReadAndCroppedAlike` failed before with
   `System.OverflowException : Negating the minimum value of a twos complement number is
   invalid`. `HduShape.BytesPer` is 0 for an HDU without axes.
2. The writer's walks copy a skipped HDU up to its header's end plus its data's blocks, and
   that sum could pass the largest offset though each term fits. The reviewer gave it as
   plausible; a header that does it was found by a search (axes of 1073741843, 2147483610 and
   4 at one byte a sample, `NAXIS1` absent: with the header, 2^63 + 1792, past the largest
   offset, 2^63 - 1).
   `R011_ASkippedHduWhoseEndPassesTheLargestOffsetIsRefusedByTheWriterToo` did not return
   within its 20 s before: the end wrapped to a negative offset, nothing was copied and the
   same header was read for ever. `FitsWriter.Copy` refuses an end before its start. The reader
   refused such a file as cut short already, so the writer meets it only when the file changed
   after the analysis.
3. Texts out of step: R-011 and ADR 0114 said `BITPIX` is checked "in an HDU with data", where
   the code asks it of an HDU with axes; the comments of `HduShape`'s sizes promised "not
   negative" for a card beyond `NAXIS`; the summaries of `SaveCrop` and `FromFits` did not name
   the new refusal; the comment of `R011_AnImpossibleHeaderNumberIsRefusedWithAMessage` now says
   that its `BITPIX = 64` and `BITPIX = 12` rows passed before the fix and stay as guards.

Left as they are:

- `docs/design/known-limitations.md`, which the plan's Records list named, is not changed: the
  branch adds no known limit. What the window's own bitmaps do with an image over 65 535 px on
  a side was not looked at, which ADR 0113 and CR-011's Status line say.
- On the Export tab the heading "JPEG: how much the image changes at each quality" stays above
  the one line "JPEG: not measured (...)" of such an image. A heading that follows the case is
  a new text, the owner's to choose.
