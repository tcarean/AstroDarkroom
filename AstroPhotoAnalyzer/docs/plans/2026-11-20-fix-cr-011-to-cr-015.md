### CR-011 An image a JPEG cannot hold is analysed without the JPEG rows

- First the measurement the entry asks for: a throw-away test (kept in the scratchpad, copied in
  for the run, removed after) takes a flat `Raster` of 65 536 x 8 through `JpegAnalyzer.Analyze`
  and shows what ImageSharp 3.1.11 does (throws, or writes a file that does not read back). The
  output is pasted in the plan's Record. Either way the fix is the same: the size is checked
  before anything is encoded.
- R-083 and R-091 (and R-114 for the tab): an image with a side over `Thresholds.JpegMaxSidePx`
  (65 535, new, the format's own limit) has no JPEG rows; the 8-bit TIFF size is still measured.
- `Analysis/JpegAnalyzer.cs`: `Analyze` returns a `JpegResult` with no rows and `TooLarge` true
  for such a raster, the TIFF size as today. `Runs/AnalysisRun.cs` needs no change.
- `Report/Recommendations.cs`, `Format`: instead of the "If the lab takes only JPEG" line, Ok:
  - `A JPEG cannot hold this image: send the TIFF.` /
    `Un JPEG nu poate tine imaginea asta: trimite TIFF-ul.`
  - because: `the image is 66000 x 3000 px, and a JPEG holds at most 65535 px on a side` /
    `imaginea are 66000 x 3000 px, iar un JPEG tine cel mult 65535 px pe o latura`
- `Report/ReportWriter.cs`, Appendix C, and the Export tab (`ResultTabs.cs`, which takes the
  sentence from the core, since a view-model writes no diagnosis), in place of the JPEG table:
  - `JPEG: not measured (the image is 66000 x 3000 px; a JPEG holds at most 65535 px on a side)` /
    `JPEG: nemasurat (imaginea are 66000 x 3000 px; un JPEG tine cel mult 65535 px pe o latura)`
  The tab's guide under the table is left out with the table.
- Tests `R083_...` in `JpegAnalyzerTests` (65 536 x 8: no rows, `TooLarge`, a TIFF size; 65 535 x
  8 still has its rows), `R091_...` in `RecommendationsTests` (the new line and its evidence, no
  q100 line), one on Appendix C, and `R114_...` in `ExportTabTests` (the tab shows the note).
- Not covered, and said so in the entry: what the window's own bitmaps (galleries, previews) do

### CR-012 A FITS header with an impossible size is refused, not followed

- R-011: the sizes of every HDU are checked before they are used: `NAXIS` between 0 and 999 (the
  standard's range), no `NAXISn` negative, `BITPIX` one of 8, 16, 32, 64, -32, -64 when the HDU
  has data, the data's byte count without overflow; the image's pixels must fit what the tool
  can hold, and its data must be in the file before memory is taken for them.
- `Input/FitsReader.cs`: one member, `Shape(hdr)`, returns the HDU's `BITPIX`, axes, planes and
  data bytes, checked; `LoadFrom`, `ReadImageHeader` and the two walks of `Input/FitsWriter.cs`
  (`FromFits`, `CropFromFits`) all read the sizes through it, so the four copies of the same
  lines become one. `LoadFrom` compares the data's length with the stream's (when it can seek)
  before `new Raster`.
- New texts (the existing `unsupported BITPIX:` and `FITS: truncated data.` are reused):
  - `FITS: the header's NAXIS1 is negative: -2.` / `FITS: NAXIS1 din header e negativ: -2.`
  - `FITS: the header's NAXIS is not between 0 and 999: 2000000000.` /
    `FITS: NAXIS din header nu e intre 0 si 999: 2000000000.`
  - `FITS: the image is too large to read: 50000 x 50000 px.` /
    `FITS: imaginea e prea mare ca sa fie citita: 50000 x 50000 px.`
- Tests `R011_...` in `FitsReaderTests`, each of the entry's five headers through `LoadFrom`
  inside a task with a time limit (the first two hang today, so the test must not): `NAXIS1 = -2`
  in an HDU that is skipped; `NAXIS = 2000000000`; 50000 x 50000; 40000 x 40000 x 3 in a 3 KB
  file (refused as truncated, no allocation); `BITPIX = -2147483648`. The negative axis also
  through `ReadImageHeader` (the `--wcs` route) and through a crop (`FitsWriter`).
  `FitsTestData.WithCard` builds the cards.

### CR-012 (ADR 0114)

Before the fix, of the nine new cases seven failed: `NAXIS1 = -2` in a skipped HDU and
`NAXIS = 2000000000` did not return within the tests' 20 s; `NAXIS = -1` and `NAXIS2 = -3` were
told as a file with no image; `BITPIX = -2147483648` and 50000 x 50000 px gave the platform's
overflow message; the header of 16000 x 16000 px in a file of two blocks was refused as cut
short only after the memory for the image was taken (the test counts the bytes allocated).
`BITPIX = 64` and `BITPIX = 12` were refused with today's sentence already and stay as guards.
The four walks (`LoadFrom`, `ReadImageHeader`, `FromFits`, `CropFromFits`) read the sizes
through `FitsReader.Shape`; `SkipExact` compares by a difference, so a large count cannot
wrap. The plan's `Shape(hdr)` returns a small record, `HduShape`. Met on the way and added to
the list as CR-081, not looked into: the heap of a table HDU (`PCOUNT`) is not counted when
the HDU is skipped. Commit 6c337bac.
