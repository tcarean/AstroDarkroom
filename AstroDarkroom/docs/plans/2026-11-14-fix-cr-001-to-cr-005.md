## What was measured (2026-11-14, throw-away programs in the scratchpad)

  the Visual C++ warning shows, in both languages. Its content laid out at 125 % and 150 % is

  150 %; the summary line takes one, the subtitle two.
- **CR-003.** A small exe marked as downloaded (the mark Explorer puts on every file it takes

  marked exe runs at once, no question, with its arguments and working folder. A direct start

  Not seen here: the prompt itself on the screen (it would have popped up on the owner's desktop).
- **CR-004.** With `vignetarea` the Romanian FlatCheck description still takes two lines at
  100, 125 and 150 % (narrowest two-line width 386 units, as before).

## Steps

One commit per entry, each with the gate green, then one commit that marks the five in the list
with their hashes. Requirement first, then the failing test, then the code.

### 1. CR-002: a half surrogate escape no longer stops the launcher

- `docs/requirements.md`: R-004 and R-007 also name a string that cannot be decoded (a `\u`
  escape that is half of a surrogate pair) among the files that give null.
- Tests (new, they fail first): `R004_AStringThatCannotBeDecoded_LeavesTheVersionsUnknown`
  in `LauncherTests.cs` and `R007_AStringThatCannotBeDecoded_GivesNoLanguage` in
  `LanguageTests.cs`, with the two files of the entry.
- Code: `ReleaseManifest.Text` (`src/AstroDarkroom.Core/ReleaseManifest.cs`) turns the
  `InvalidOperationException` of `GetString()` into a `JsonException`, which both `TryRead`
  filters already catch: a `WARN` line with the exception, null. Narrow on purpose: no other
  `InvalidOperationException` is swallowed.
- `docs/design/launcher.md`: the sentence on what makes `TryRead` return null.

### 2. CR-004: one spelling, `vignetarea`

- R-001's quoted Romanian description of FlatCheck, the expected text in
  `R001_Catalogue_ListsTheSixAppsInWorkflowOrderWithTheirTexts` (at the owner's word) and
  `AppCatalogue.cs`. One word changes:
  - now: `... expunerea, simetria, vinietarea fata de profilul obiectivului ...`
  - after: `... expunerea, simetria, vignetarea fata de profilul obiectivului ...`
- ADR 0028 (the spelling is FlatCheck's own; the measurement above).

### 3. CR-003: the tools start directly

- R-003: the window starts the plan directly, not through the shell, so Windows' question
  about a downloaded program, answered once for the launcher, is not asked again for each tool.
- Test (fails first): `R003_TheStartIsDirect_NotThroughTheShell` on a new core function
  `Launcher.StartInfo(LaunchPlan)`, which returns the `ProcessStartInfo` (file, working folder,
  arguments, `UseShellExecute` false). The core still starts nothing.
- Code: `MainWindow.OpenApp` passes `Launcher.StartInfo(plan)` to `Process.Start`. The runtime
  link keeps the shell (it opens a web address). The catches stay as they are (CR-006 is
  theirs).
- Docs: ADR 0027 with the measurement; `launcher.md`; the comments of `LogText.Open` and
  `OpenApp`. The READMEs already say SmartScreen asks at the first start, which is now true.

### 4. CR-005: the main window fits its screen

- New requirement R-020: the main window is never taller than the work area of the screen it
  opens on and opens inside it; when its content is taller, the rows scroll (wheel, and a row
  reached with Tab comes into view) while the top bar and the bottom bar stay in view. R-012
  gains the main window's own work area and `rows scroll: yes|no` in its `window shown` line.
- Tests (fail first): `R020_TheRowsScrollBetweenTheTwoBars`, which reads
  `MainWindow.xaml` and checks that the rows sit in a scroll viewer in the one stretching row,
  the bars in rows of their own; `R020_...` rows on `WindowFit.Top` with the measured heights.
  The window itself has no test project (ADR 0001): it is shown by the harness, below.
- Code, as "Despre" does it (reusing `ScreenArea.WorkAreaOf` and `WindowFit.Top`):
  `MainWindow.xaml` gets rows `Auto, *, Auto` and a `ScrollViewer` (transparent, not focusable,
  bar on `Auto`) around `Rows`; `MainWindow.xaml.cs` caps `MaxHeight` at its screen's work area
  when the window gets its handle, moves `Top` through `WindowFit.Top` on `Loaded`, and logs
  the area and whether the rows scroll.
- Docs: ADR 0029 with the measurements; `launcher.md`; `logging.md`; the summary of `WindowFit`.

### 5. CR-001: the rule, no code

- `docs/skills.md`, at `/release` and at `/wrap-up`'s publish: a package published with
  `-PublishOnly` under another number than `<Version>` is a trial and is never handed out; the
  trial publish uses `<Version>` for `X.Y.Z`.
- ADR 0026: the owner's choice and the alternatives not taken (the launcher saying both
  numbers; the kit's script giving the publish the number).

## What deviated

- The ADRs took their numbers in the order of the commits, not the plan's: 0026 the spelling
  (CR-004), 0027 the direct start (CR-003), 0028 the main window (CR-005), 0029 the rule
  (CR-001). Commits: CR-002 b8f5a26c, CR-004 395a788a, CR-003 f548982b, CR-005 176c68e7,
  CR-001 91f3beb0.
- CR-005, the fit is made on `SourceInitialized`, not on `Loaded` as the plan said after
  "Despre": the measuring program showed that WPF raises `Loaded` first for a window sized to
  its content and undoes a `Top` set there. The log's line moved to `ContentRendered`. That
  "Despre" has the same order is the new entry CR-023 of the list, left open.
- CR-005, the scroll viewer has a template of its own, which the plan did not have: with the
  default one the scroll bar took 17 DIP from the rows and one Romanian description went to
  three lines at 125 %.
- CR-002, the first test is a theory of two files (a component's key and the suite's `name`).
- The review of the branch by a subagent (2026-11-14) found CR-002 half fixed: the escape in a
  key, not a value, still threw, from `TryGetProperty`. Fixed with the tests first
  (`ReleaseManifest.Find`). Its other findings were sentences: the button, not the row, comes
  into view with Tab; stale mentions in `launcher.md` and `ScreenArea.cs`; the handles a direct
  start lets a tool inherit, added to ADR 0027. The rows of
  `R020_TheMainWindowsTopKeepsItInsideTheWorkArea` could not fail first, whatever step 4 says:
  `WindowFit.Top` was there already; they now carry the heights the window really hands over.
- Verification: the measuring program gave the window its work areas through its own `FitInto`;
  no real screen at 125 % or 150 % was used and Tab was not pressed by hand. The launcher was
  not started by hand from a published suite folder: the owner was at the PC.
- Two things the measuring programs did on the owner's desktop, not meant: one asked a hidden
  window for the keyboard focus (eight windows in each of two runs), and one probe window,
  centred on an owner off the screen, was placed by WPF on the left screen for a moment. Both
  steps were removed.
