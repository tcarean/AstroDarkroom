# Requirements

The source of truth for behaviour. Code follows this file, not the reverse. A behaviour change is
first an edit here (status `draft`), then a test, then code (status `implemented`).

Rules for entries:

- IDs are `R-NNN`, assigned once, never reused. A dropped requirement keeps its ID with status `dropped`.
- Status is one of `draft`, `accepted`, `implemented`, `dropped`.
- Describe observable behaviour, with one concrete example. No adjectives.
- Tests carry the ID in their name: `R001_Catalogue_ListsTheSixAppsInWorkflowOrder`.
- Error behaviour is a requirement too.

The suite folder is the folder the launcher runs from (its own base directory): the flat folder
`scripts/release.ps1` publishes, with every component's executables beside `AstroDarkroom.exe`.

| R-001 | implemented | `AppCatalogue.Apps` lists the six apps in workflow order, each with its folder name, a Romanian title, a one-line Romanian description, the file name of its window exe and its icon (R-010): DarksCheck, "DarksCheck", "Verifica dark-urile unei sesiuni sau ale unei biblioteci", `DarksCheck.Wpf.exe`; FlatCheck, "FlatCheck", "Verifica flat-urile unui obiectiv", `FlatCheck.Wpf.exe`; LightsCheck, "LightsCheck", "Verifica light-urile unei sesiuni: focus, trailing, dithering, drift", `LightsCheck.Wpf.exe`; ImageVisualCompare, "ImageVisualCompare", "Compara doua variante ale aceleiasi procesari, pixel cu pixel", `ImageVisualCompare.Wpf.exe`; WCS_Copy, "CopyWcs", "Copiaza plate solve-ul unui FITS in altul", `CopyWcs.Wpf.exe`; AstroPhotoAnalyzer, "AstroPhotoAnalyzer", "Verifica o imagine finala inainte de print", `AstroPhotoAnalyzer.Wpf.exe`. The suite ships the windows only; the consoles stay in each component's own release (ADR 0002). The exe names are those the components' project files build (`SuiteTests`). The descriptions quoted are the Romanian wordings; the English ones are in R-006. |
| R-002 | implemented | `SuiteFolder.Locate(app)` says an app is available when a file named like its window exe exists in the suite folder, and gives its full path; otherwise the app is unavailable and the reason is `Lipseste <window exe>`. Example: a suite folder with `DarksCheck.Wpf.exe` and nothing else: DarksCheck available at `<folder>\DarksCheck.Wpf.exe`, FlatCheck unavailable with the reason `Lipseste FlatCheck.Wpf.exe`. A console exe of a component's own release, such as `flatcheck.exe`, plays no part. The reason quoted is the Romanian wording; the English one is in R-006. |
| R-003 | implemented | `Launcher.Plan(app, folder)` gives, for an available app, the file to start (the window exe's full path) and the working directory (the suite folder); for an unavailable app it throws `InvalidOperationException` carrying the reason of R-002. The core only plans the start; the window executes it with `Process.Start`. |
| R-004 | implemented | `ReleaseManifest.TryRead(path)` reads the `release.json` `scripts/release.ps1` writes: the suite's name, version, date and commit, and each component's name, version, commit, `unreleased` and `clean`. Example: a file with version `0.1.0` and one component `FlatCheck` at `2.3.0` with `unreleased: true` gives those values. A missing file, a file that is not JSON, or one without a `components` array gives null, and a missing or mistyped key in a component gives `""` or `false` for that key; the launcher runs the same with or without the file, showing the versions as unknown. The window shows each component's version only; `unreleased` and `clean` are read for `release.json`'s sake and not shown. |
| R-005 | implemented | Every source file (`.cs`, `.xaml`, `.py`) under the code, test and `Icon/` folders starts with the GPL notice: the SPDX line, the copyright line and the three standard paragraphs, as `LicenseHeaderTests` spells them; a `.py` keeps its shebang and a `.xaml` its XML declaration on the first line. `LICENSE` is the full GPL v3 text. Example: `src/AstroDarkroom.Core/Version.cs` begins with `// SPDX-License-Identifier: GPL-3.0-or-later`. |
| R-006 | implemented | Every text the launcher shows exists in English and in Romanian without diacritics, and `Ui.Current` picks the wording: the innermost `Ui.Use(language)` scope on the current flow, else `Ui.Default`, which is English (`Ui.StartupDefault`) until the start-up sets it. The catalogue's descriptions, the reason of R-002, the message of R-003 and the warranty of "Despre" follow it; the folder names, titles and exe names do not. Example: in English `AppCatalogue.Apps[1].Description` is `Checks the flats of a lens` and the reason for a missing FlatCheck is `FlatCheck.Wpf.exe is missing`; in Romanian they are what R-001 and R-002 quote. The window has a language selector (`English`, `Romana`) in its bottom bar; a change applies to every visible text at once, without a restart. The tests run in Romanian (a module initializer), so the Romanian wordings quoted in R-001 to R-003 are asserted unchanged (ADR 0006). |
| R-007 | implemented | `LanguageSetting.TryRead(path)` reads the file `{ "language": "ro" }` (or `"en"`, case-insensitive) and gives that language. A missing file, a file that is not a JSON object, one without a `language` key, a non-string value or an unknown code gives null, and the launcher starts in English. `LanguageSetting.Write(path, language)` writes `{"language":"<code>"}` through a temporary file replaced in one move, creating the file's folder; a write that fails is ignored, so the choice holds for the run and is asked again at the next. The window reads `%LOCALAPPDATA%\AstroDarkroom\settings.json` before it opens and writes it at every change of the selector. |
| R-008 | implemented | `LaunchPlan` carries the arguments of the start as one string: `Launcher.Plan(app, folder)` gives `--lang=ro` in Romanian and `--lang=en` in English, the form every component's window accepts, and the window passes it to `Process.Start`, so a tool opened from the launcher speaks the launcher's language. Example: in Romanian the plan of LightsCheck is `<folder>\LightsCheck.Wpf.exe` with the one argument `--lang=ro`. |
| R-009 | implemented | `Prerequisites.Summary` is one line and `Prerequisites.Details` three paragraphs, each in both languages through `Ui.T`, saying what the suite needs: a Siril session folder (`lights/`, `darks/`, `flats/`, `biases/`, the scripts' results in `process/`), Siril 1.4.4 or newer installed, and, optional for FlatCheck, Adobe's lens profiles with the programs that install them (Lightroom, Photoshop with Camera Raw, the free Adobe DNG Converter). Example: in English the second paragraph starts with `Siril 1.4.4 or newer installed`. |
| R-010 | implemented | `SuiteApp.Icon` names the app's icon, a file of this repository's `Icon/` folder that is a copy of the component's own icon, the `ApplicationIcon` of its window project, under the same file name: `darkscheck.ico`, `flatcheck.ico`, `lightscheck.ico`, `ImageVisualCompare.ico`, `copywcs.ico`, `AstroPhotoAnalyzer.ico`; `SuiteTests` checks that each copy has the component's bytes (ADR 0011). The window shows the icon at the left of the app's row, 40 px, and dims it with the button when the app is missing from the suite folder (R-002). Example: the row of DarksCheck shows `Icon/darkscheck.ico`, the icon `DarksCheck.Wpf.exe` carries. |
| R-011 | implemented | Every start of the launcher writes a plain-text log, UTF-8 without BOM, in a folder `log` beside `AstroDarkroom.exe`, or in `%LOCALAPPDATA%\AstroDarkroom\log` when that folder cannot be created or written or its newest file cannot be appended to (the first line says which). The file names begin with the executable's name: the first file is `AstroDarkroom.log`, and when the file being written passes 1 MiB the next one is started (`AstroDarkroom_01.log`, `AstroDarkroom_02.log`, ...); at most 5 files are kept, the oldest deleted first, and the next start goes on in the newest. The rolling never deletes another executable's files in the same folder, such as the `FlatCheck.Wpf.log` FlatCheck writes there when it runs from the suite folder, and a file another launcher holds open is shared, not a reason to fall back (ADR 0012). Example: 8 MiB of lines through the launcher's configuration leave `AstroDarkroom_03.log` to `AstroDarkroom_07.log`, none above 1 MiB plus one line, the last line in `AstroDarkroom_07.log`, where the next start writes too. |
| R-012 | implemented | The log holds what a bug report needs, in English with invariant numbers whatever the interface language, an exception's message as the user was shown it: a first line per start with the executable, its version, its path, the arguments verbatim, the working folder, the log folder, the level, the OS, the processors, the memory, the .NET runtime, the culture, the time zone and the process id; the language the launcher starts in and where it came from, the setting file and the suite folder; `release.json` read, with the suite's name, version, date and commit and every component's name, version and commit, or why it gave nothing (missing, not a manifest, unreadable); the setting file read or written, or why not; at every build of the rows, how many of the six apps are in the suite folder and which window exes are missing; the window's size, position, work area and DPI once shown; each language switch; each start the user asks for, with the file, the arguments and the working folder, and its outcome, the started process's id or the exception; About opened and closed; the window closing; every exception, those the launcher recovers from included, with its type, message and stack, an unhandled one at `FATAL` and the same one once; and a last line with the exit code and the elapsed time. Example: opening FlatCheck from the suite folder `E:\suite` in Romanian writes `Window open FlatCheck: E:\suite\FlatCheck.Wpf.exe --lang=ro in E:\suite\`, then `Window started FlatCheck.Wpf.exe, process 31708`. |
| R-013 | implemented | The log level is `Debug` unless the environment variable `ASTRODARKROOM_LOG` names another, in any case, spaces around it ignored: `off`, `fatal`, `error`, `warn`, `info`, `debug` or `trace`; any other value means `Debug`. `off` creates neither the folder nor a file. Example: with `ASTRODARKROOM_LOG=off` a start leaves the folder beside the executable as it was. |
| R-014 | implemented | Two launchers writing the same log file at full speed both keep every line, each whole and once, across the 1 MiB roll too: the log is written through `NLog.Targets.AtomicFile`, which leaves the operating system to place every write at the end of the file, in the build the window ships (`net8.0-windows`), which the tests load (ADR 0012). Example: two writers of 4000 lines each, released together, leave 8000 whole lines in `AstroDarkroom.log` and `AstroDarkroom_01.log`, every number of each writer once, the two writers' lines interleaved. |
| R-015 | implemented | "Despre" lists the components written by others that the launcher ships, under `THIRD-PARTY COMPONENTS` / `COMPONENTE TERTE`, each with its role, its licence, its copyright line and its project's address: today one, NLog with its file target `NLog.Targets.AtomicFile`, BSD-3-Clause, `Copyright (c) 2004-2024 Jaroslaw Kowalski <jaak@jkowalski.net>, Kim Christensen, Julian Verdurmen`, `https://nlog-project.org/`. `ThirdParty.Components` is the list; together its entries claim each package the core references exactly once, and `THIRD-PARTY-NOTICES.md` has a section for each, with the licence's whole text (`ThirdPartyTests`, ADR 0013). |
