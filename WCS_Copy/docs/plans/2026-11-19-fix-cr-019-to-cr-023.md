| Entry | What goes wrong today |
| --- | --- |
| CR-019 | a source's `WCSAXES` is appended after a destination's own WCS cards; the FITS standard (4.0, section 8.2) says it must precede them |
| CR-020 | the SIP keys `A_DMAX` and `B_DMAX` are in neither list: never copied, never dropped |
| CR-021 | the SIP pattern `^(A|B|AP|BP)_\d+_\d+$` takes `A_1_2` followed by a line feed (`$` matches before a final `\n`): the key is copied or dropped, and its raw line feed splits a log line and the drop line |
| CR-022 | `AsciiText.Of` keeps control characters, so a source named with 0x7F (Windows allows it) puts that byte into the HISTORY card |
| CR-023 | `--help` writes the usage with bare LF line ends (a raw string literal, the repository forces LF) inside CRLF output |

**The owner's answers (2026-11-19), each the recommended option:**

1. CR-020: `A_DMAX` and `B_DMAX` join the WCS list (32 keys): copied when the source has them,
   dropped from the destination when it does not (R-016), as `A_ORDER`.
2. CR-022: each control character of the source's name is one `?` in the HISTORY card.

**Measured before asking (2026-11-19):**

- A read-only scan of the primary headers of the 5,206 FITS files under `E:\Photografie`
  (63 s, a script in the scratchpad): 257 hold a SIP solve (`A_ORDER`); none holds `WCSAXES`,
  none `A_DMAX` or `B_DMAX`, and no keyword holds a control character. The five cases come from
  other programs' files (astrometry.net writes `WCSAXES`) or crafted ones.
- CR-019, astropy 8.0.1 (WCSLIB): `WCS(header)` gives the same axes and coordinates whether
  `WCSAXES` stands before or after the other WCS cards: `NAXIS = 2` with `WCSAXES = 3` gives 3
  axes in both places, `NAXIS = 3` with `WCSAXES = 4` gives 4 in both, and astropy's
  `verify('exception')` passes both. No reader measured minds, so the entry stays severity 4;
  Siril was not measured.

## The text (approved with the answers)

CR-022 changes one card the tool composes, for a source named `a` + 0x7F + `b.fit`:

| Today | Proposal |
| --- | --- |
| `HISTORY WCS copied from a<0x7F>b.fit` (the byte 0x7F in the card) | `HISTORY WCS copied from a?b.fit` |

No interface text changes: CR-021's drop line and CR-023's usage keep their words; CR-023
changes only line ends.

## Assumptions (say so at review if one is wrong)

- CR-019: `WCSAXES` must stand above every card of the target whose keyword is a WCS key of
  R-007 or a SIP coefficient (one predicate, `WcsMetadataKeys.IsPlateSolveKey`, which
  `SelectKeysToDrop` then uses too). After the cards are set, when the copy set `WCSAXES`, it is
  moved right above the first such card when one stands above it, a destination's own `WCSAXES`
  the copy replaces included; otherwise nothing moves. Keys outside both lists (`PVi_m`,
  `CTYPE1A`) are not looked at. A valid header has its mandatory cards first, so `WCSAXES`
  never goes above `NAXISn`. No new log line: the Trace of the cards written shows the order.
- CR-020: the two keys go after `BP_ORDER`, before `PLTSOLVD`, and count as WCS keys in the
  log's `selected` line, as the orders do. V-001's figures do not move (Siril writes neither).
- CR-021: the pattern becomes `^(A|B|AP|BP)_[0-9]+_[0-9]+\z`. `[0-9]` changes nothing a file
  can hold (Latin-1 has no other decimal digit) but says what the pattern means; the line feed
  is the shown case. A keyword with a control character is then no key of the lists: neither
  copied nor dropped, as R-010 already keeps such a card apart. No log escaping is added, since
  every key a log line names is then a literal of the lists or matches the strict pattern.
- CR-022: every character below 0x20, and 0x7F, becomes one `?`; the space stays.
- CR-023: each language's usage stays one raw string (its columns aligned by hand) and is
  written with its line ends replaced by the writer's own (`ReplaceLineEndings(writer.NewLine)`),
  so the bytes of the source file do not matter.
